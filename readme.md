# Predicting Electric Vehicle Purchases

Machine learning project for predicting whether a customer will purchase an electric vehicle. The project combines customer, commuting, vehicle, charging, and environmental signals to estimate purchase propensity and produce competition-ready probability submissions.

This is a notebook-first ML project that is being evolved into a complete production-style system with reproducible training, experiment tracking, model versioning, CI/CD, containerization, and an inference API.

## Why This Project

Electric-vehicle adoption is influenced by more than income or age. This project explores how charging access, commute distance, current vehicle ownership, subsidies, environmental concern, and range anxiety combine to influence purchase intent. The modeling work compares multiple tree-based approaches and blends their probability predictions to improve ranking quality.

## Project Highlights

- Performed exploratory data analysis across numerical and categorical customer features.
- Investigated numerical skewness and prepared separate numerical and categorical preprocessing paths.
- Built an imbalanced-learn pipeline with scaling, one-hot encoding, and SMOTE.
- Trained an XGBoost classifier and evaluated probability predictions with ROC-AUC.
- Tuned XGBoost with `RandomizedSearchCV`, stratified cross-validation, and a holdout comparison.
- Trained CatBoost with native categorical-feature support and out-of-fold predictions.
- Compared XGBoost, CatBoost, and Random Forest predictions.
- Tested weighted and rank-based blending strategies for submission generation.
- Applied SHAP with a tree explainer to inspect feature contributions.
- Generated multiple submission candidates with the required `id,Will_Buy_EV` schema.

## Dataset

The training data contains customer demographic, financial, commuting, vehicle, charging, and environmental features.

### Target

- `Will_Buy_EV`: binary purchase outcome (`Yes`/`No` in the raw training data)

### Identifier

- `id`: record identifier; it should be preserved for submission output but excluded from model features.

### Numerical features

`Age`, `Annual_Income_USD`, `Daily_Commute_km`, `Number_of_Cars_Owned`, `Charging_Stations_Near_Home`, `Charging_Stations_Near_Work`, `Environmental_Concern_Level`, and `Range_Anxiety_Level`.

### Categorical features

`Gender`, `City_Type`, `Current_Car_Type`, `Home_Charging_Possible`, and `Subsidy_Available`.

## Setup

Python 3.10 or newer is recommended.

```powershell
conda create -n ev-purchase python=3.10
conda activate ev-purchase
pip install -r requirements.txt
```

The repository includes large CSV files under `data/raw/`. Keep the expected file names and paths unchanged unless the configuration in `configs/data_configs.py` is updated as well.

## Current Usage

The currently usable workflow is notebook-based:

```powershell
conda activate ev-purchase
jupyter notebook notebook\model2_fixed.ipynb
```

The notebooks load the dataset, inspect the features, train experimental models, and write prediction/submission outputs. Depending on the notebook, input paths may need to be adjusted to `data/raw/train.csv` and `data/raw/test.csv`, because the repository stores the datasets under `data/raw/`.

There is no working `python main.py` or FastAPI server yet.

## MLOps Blueprint

The intended production architecture is organized around reproducibility and a single source of truth for preprocessing:

```text
Raw CSV data
	|
	v
Data validation and ingestion
	|
	v
Preprocessing and feature engineering
	|
	+--> Versioned processed data and parameters
	|
	v
Model training and cross-validation
	|
	+--> Metrics, plots, and experiment record
	|
	v
Model selection and artifact registry
	|
	v
FastAPI prediction service <--> Frontend prediction form
	|
	v
Containerized deployment, logging, monitoring, and drift checks
```

The planned MLOps stack uses DVC for data and pipeline versioning, YAML configuration for reproducible parameters, serialized model artifacts for inference, FastAPI for serving, Docker for packaging, and automated tests/CI for quality gates. The design keeps the preprocessing object alongside the model so training and inference apply identical transformations.

## Planned End-to-End Workflow

1. Validate schema, data types, missing values, duplicates, and target balance.
2. Load `data/raw/train.csv` and `data/raw/test.csv` through the shared ingestion module.
3. Remove duplicates and exclude `id` from model features while preserving it for submissions.
4. Handle missing values, encode categorical columns, transform skewed features, and apply imbalance handling.
5. Create and persist processed datasets in `data/processed/`.
6. Train the configured model using the same preprocessing pipeline used during experimentation.
7. Evaluate with stratified cross-validation, ROC-AUC, precision, recall, F1, confusion matrix, and calibration checks.
8. Save the selected model and preprocessing artifact to `models/model.pkl` and metrics to `artifacts/metrics.json`.
9. Track datasets, parameters, metrics, and pipeline stages with DVC.
10. Add a FastAPI endpoint in `main.py` for validated single-record predictions and health checks.
11. Connect the frontend form to the API with loading, validation, and error states.
12. Add unit, data-contract, pipeline, and API tests plus CI quality gates.
13. Build and run the service through Docker, then add request logging and basic model/data monitoring.

## Dependencies

The main libraries are pandas, NumPy, scikit-learn, imbalanced-learn, XGBoost, CatBoost, joblib, FastAPI, Uvicorn, Pydantic, and DVC. Install them with `pip install -r requirements.txt`.

## Outputs

Submission files use the schema:

```text

```

Use `data/raw/sample_submission.csv` as the reference schema when creating new submissions. Generated submissions should be written to `data/submission-files/` and should retain the test-set IDs.
